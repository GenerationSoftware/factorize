Use the remote **Streamable HTTP** endpoint:

```text
https://app.factorize.sh/mcp
```

Complete [browser account and execution setup](/quickstart) first. Factorize requires OAuth authorization, owner membership and tenant-bound scopes. A JSON configuration from one client is not a universal MCP configuration.

## Codex

Current Codex supports Streamable HTTP and OAuth. Add this client-specific TOML to `~/.codex/config.toml`:

```toml
[mcp_servers.factorize]
url = "https://app.factorize.sh/mcp"
```

Run `codex mcp login factorize`, then use `/mcp` in Codex to verify the connection. See the [official Codex MCP documentation](https://developers.openai.com/codex/mcp) for configuration and OAuth support.

## Claude Code

Add the remote server:

```bash
claude mcp add --transport http factorize https://app.factorize.sh/mcp
```

Start Claude Code, enter `/mcp`, choose Factorize and authenticate when prompted. See the [official Claude Code MCP documentation](https://code.claude.com/docs/en/mcp) for HTTP transport, OAuth and configuration scope.

## Authorize in the browser

The client opens Factorize authorization in your browser. Sign in with your verified Factorize email/password and approve the requested scopes. Select `triggers:read` for discovery, `triggers:write` for edits, `runs:read` for inspection, `runs:invoke` for Trigger invocation, `runs:start` for direct runs, and `runs:cancel` for cancellation. Integration and skill operations use their respective scopes. Read-only access cannot create or invoke triggers. Return to your client after consent.

Consent lists 12 permissions, including `runs:write` for renaming runs. Run write grants also retain invocation and cancellation access for compatibility. Write does not imply read. If you need to create an account or verify your email, finish those steps and restart client authorization; do not assume the signup screen will automatically resume the original request. No Linear or execution token belongs in the MCP client.

Ask **“List my Factorize triggers.”** The agent should call `list_triggers({})`. An empty `items` list is a successful connection to a workspace with no triggers. Next ask it to list execution integrations and follow the [first-trigger walkthrough](/quickstart).

Other clients must support remote Streamable HTTP and Factorize's OAuth discovery/PKCE flow. Their UI and plan availability vary; consult their own documentation rather than pasting either configuration above.

## Team skills

Factorize publishes every active team skill using the [MCP Skills extension](https://skills.extensions.modelcontextprotocol.io/specification/beta/skills), `io.modelcontextprotocol/skills`, on protocol revision 2026-07-28 or later. A compatible client sees the declaration in `server/discover`, pages through `skills/list`, and refreshes individual entries with `skills/get`. These methods and each `resources/read` require `skills:read` and an active authorized identity.

Skill URIs have the form `skill://teams/TEAM_ID/SKILL_NAME/SKILL.md`. Each entry includes the full frontmatter and a complete manifest with SHA-256 digests and byte lengths. Read supporting files at the URIs in that manifest. Files remain separate resources; Factorize does not execute their scripts. Editor and successful Git publications are visible on the next read. A failed publication preserves the last valid package. Renaming removes the previous URI.

Literal skills without frontmatter receive a published `name` and description wrapper. Existing author metadata is retained, with the shared team name authoritative after a rename. Stored instructions and existing run snapshots are preserved. Skill metadata has no VM dependency.

Factorize-managed Pi uses this same MCP session boundary. Its short-lived identity is bound to the active run and current execution lease, with application scopes and selected integrations taken from the accepted run snapshot. Cancellation, lease replacement, owner revocation and integration disconnection are checked on subsequent requests. Provider credentials never enter the model context.

Selected run skills are pinned inputs under `skill://runs/TEAM_ID/RUN_ID/SKILL_NAME/SKILL.md`, including their supporting files. An active run may discover and read these inputs even with no `skills:read` permission. That capability grants access only to its own accepted package. Broader team-library discovery still requires `skills:read`. Unrelated edits, renames or deletes do not replace the run's pinned inputs.

## Proxy tool discovery

Integration APIs are available through `request_api`, without a VM, shell, or raw
OAuth credential. Call `get_api_reflection` first and pass an integration's
`requestExample` to `request_api`. Use `read_api_response` for retained handles.
The proxy tools remain discoverable when `proxy:use` has not been granted; calls
then fail with `insufficient_scope` and require renewed consent. `forbidden`
indicates integration policy; `credential_unavailable` asks the owner to repair
upstream credentials.

If reflection is available but proxy tools are missing, compare authenticated
server `tools/list` with the connector's catalog. From a repository checkout,
pipe the captured JSON into `node scripts/diagnose-mcp-proxy.mjs`. This diagnostic
makes no network calls. If server discovery includes the missing tools, refresh
or reconnect the client connector; otherwise check the deployed server version.
A saved connector catalog can differ from the current repository. Local fixture
acceptance verifies the protocol contract, not a particular mobile app release.
