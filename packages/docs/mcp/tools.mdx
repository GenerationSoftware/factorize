## Events and occurrences

`list_events` and `get_event` discover Event definitions and their payload
schemas. `create_event` and `update_event` manage those definitions. Each Event
may have multiple Triggers. An enabled Trigger publishes an occurrence only
after validating the payload against the Event's current JSON schema.

Subscribe to `factorize://events/{eventId}/occurrences` using MCP resource
subscription support. After a resource-updated notification, read the resource
to retrieve durable data. `list_event_occurrences` lets a reconnecting client
recover stored records.

`delete_event` permanently removes the Event, all attached Triggers and input
configurations, and all stored occurrences.

## Triggers

A Trigger belongs to one Event and watches a schedule, signed webhook/provider
input, or manual fire request. Duplicate deliveries are deduplicated. Reuse the
same `idempotencyKey` after an uncertain manual fire. Webhook activity tools
show safe processing outcomes without exposing secrets or raw payloads.

`create_trigger` and `update_trigger` accept a parent `eventId` and source
configuration. Read a Trigger before replacing its configuration. Skills remain
standalone and are not part of a Trigger's execution configuration.

## Skills and integration APIs

Skill tools manage standalone team instruction documents. Integration tools
use server-held credentials and current authorization; credentials are never
returned. `get_api_reflection` describes available integrations and safe request
examples before `request_api` is used. See [REST reference](/api/reference) for
exact request and response schemas.
