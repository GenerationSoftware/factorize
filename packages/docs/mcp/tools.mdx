Connect to `https://app.factorize.sh/mcp` using [client authorization](/mcp/overview). Tools return text containing JSON and the same JSON in `structuredContent`. Array service results are wrapped as `{"items":[...]}`; object results retain their fields. Examples below show structured content, sometimes with selected fields only. Identifiers such as `JOB_ID` are placeholders: use returned identifiers, never invented values.

## Discovery inputs and outputs

- get_team exposes Team defaults. Select optional workspace configurations in the browser; model integration and model selection are independent of VM configuration.
- `list_exe_connections({})` returns safe connection IDs and available tags, never API tokens, guest agents or model catalogs.
- `list_github_installations({})` → `{"items":[{"installationId":12345,"accountLogin":"YOUR_ORG","state":"active"}]}` (selected fields). Use numeric `installationId` in GitHub events; choose repository IDs in the browser.
- `list_cloudflare_tail_integrations({})` → `{"items":[{"integrationId":"INTEGRATION_ID","name":"Worker errors","referencedTriggerCount":0}]}` (selected fields). Use `integrationId` in Tail event configuration.
- `diagnose_exe_integration({"connectionId":"CONNECTION_ID"})` checks documented account permissions and returns ok, connectionId and permissions. It does not install/probe agents or models. Image verification in the browser uses a disposable VM to check workspace prerequisites and cleanup. Missing connections return not_found.

## Trigger fields and creation

| Field | Contract |
| --- | --- |
| `name` | Required Agent Skills name, 1–64 lowercase letters/digits and single hyphens; shared team namespace; `manual` is reserved |
| `prompt` | Optional literal text, max 50,000 characters |
| `skillId` | Optional skill UUID or null; at most one skill |
| `executionConfigId` | Optional VM configuration ID; inherits the Team default |
| `vmImage` | Optional public Docker/OCI image reference for exe.dev triggers. Omit or send an empty value to use the exe.dev default. Verification is available in the browser trigger editor. |
| `runNameTemplate` | Optional string, max 500; defaults to empty |
| `concurrencyLimit` | Optional integer 1–50; defaults to 1 |
| `model` | Optional trimmed string, max 120; defaults to empty/provider default |
| `effort` | Optional trimmed string, max 40; choose target-supported values |
| `events` | Optional array, max 50; defaults to empty and server supplies a manual event |

Do not submit credentials, unknown top-level fields, parameters or parameter overrides. Event objects contain `kind`, `config`, optional Mustache `template`, optional `enabled` (default true), and optional `id`/`slug` for preservation during edits. Kinds/configuration:

- `manual`: `{}`.
- `schedule`: `{"cron":"0 9 * * 1-5","timezone":"UTC"}`.
- `webhook`: provider-specific configuration below, optional `conditions`.
- `triggerLifecycle`: `{"sourceTriggerIds":["SOURCE_JOB_ID"],"states":["succeeded"]}`. States: `succeeded`, `failed`, `stopped`, `edited`.

Webhook configurations:

```json
[
  {"provider":"linear","projectId":"PROJECT_ID","matchRules":[{"type":"status","targetId":"STATUS_ID"}]},
  {"provider":"clickup","listId":"LIST_ID","matchRules":[{"type":"assignee","targetId":"USER_ID"}]},
  {"provider":"github","installationId":12345,"repositoryId":67890,"event":"pull_request","action":"opened"},
  {"provider":"cloudflareTail","integrationId":"INTEGRATION_ID"}
]
```

Match rule types: `owner`, `creator`, `status`, `label`, `assignee`, with non-empty string `targetId`. Linear/ClickUp require at least one rule; GitHub requires at least one rule or both event/action. Select actual resource IDs in the browser editor. This array illustrates alternative configurations, not a tool input.

`create_trigger` input:

```json
{
  "name": "review-recent-changes",

  "executionConfigId": "TARGET_ID",
  "concurrencyLimit": 1,

Full trigger results include prompt/configuration, timestamps, agent metadata and event reflection. `list_triggers({})` returns `{"items":[...triggers]}`; `get_trigger({"triggerId":"JOB_ID"})` returns a single trigger. Creation errors include `conflict` for duplicate slug and `invalid_request` for invalid/unknown target or invalid fields. If creation's response is lost, list/find the trigger before recreating it.

## Safe replacement and enable/delete

`update_trigger` replaces configuration. Fetch first; preserve all intended fields and events; strip read-only fields. Example for a manual-only trigger:

```json
{
  "triggerId": "JOB_ID",
  "expectedUpdatedAt": "2026-10-10T09:00:00.000Z",
  "name": "review-recent-changes",
  "prompt": "Clone REPOSITORY_URL and review the latest commit. Run relevant checks.",
  "executionConfigId": "TARGET_ID",
  "runNameTemplate": "",
  "concurrencyLimit": 1,
  "model": "",
  "events": [
    {
      "id": "TRIGGER_ID",
      "slug": "event-1",
      "kind": "manual",
      "enabled": true,
      "config": {}
    }
  ]
}
```

Result is the saved trigger with new `updatedAt`. Preserve any automatic events too. Omission can reset optional settings or remove automatic events. On `stale_trigger`, fetch/reapply; omitting `expectedUpdatedAt` is last-writer-wins. Stable slugs survive edits when event identity/kind is retained; changing kind creates a new event identity. Inspect returned slugs rather than assuming numbering.

`enable_trigger({"triggerId":"JOB_ID"})` → `{"id":"JOB_ID","enabled":true}`; `disable_trigger({"triggerId":"JOB_ID"})` → `{"id":"JOB_ID","enabled":false}`. `delete_trigger({"triggerId":"JOB_ID"})` → `{"id":"JOB_ID","deleted":true}`; existing runs retain their history and artifacts. Missing triggers return `not_found`. Saves can emit `edited` events; see [chaining](/recipes/chaining).

## Invocation, run inspection, and retries

`invoke_trigger` input:

```json
{"triggerId":"JOB_ID","name":"First review","prompt":"Focus on regressions","data":{"branch":"main"},"idempotencyKey":"review-first-1"}
```

Result:

```json
{"invocationId":"INVOCATION_ID","runId":"RUN_ID","state":"queued","duplicate":false}
```

Optional `name`: trimmed 1–120 characters; `prompt`: max 50,000, default empty; `data`: JSON object; `idempotencyKey`: trimmed 1–200 characters and must not begin `manual:`. Retrying the same key for the same trigger returns the original IDs with `duplicate:true`, even if that run failed. Without a key, each call is a new invocation. Intentional reruns require a new key. Manual requests never coalesce; `queue_full` means capacity is exhausted. Disabled manual events return `operation_failed`.

`list_runs({"triggerId":"JOB_ID","state":"failed","contextQuery":"regression","limit":10})` → `{"items":[{"id":"RUN_ID","trigger_id":"JOB_ID","state":"failed"}],"nextCursor":null}` (selected fields). Pass a returned cursor for later pages. `limit` is 1–100, default 50; `contextQuery` is 1–50,000 characters and case-insensitive substring matching. The current repository uses SQL ILIKE: percent and underscore behave as wildcards; use get_run for full context. Current results do not include excerpts.

Allowed state filters: `queued`, `starting`, `running`, `done`, `blocked`, `failed`, `ignored`, `succeeded`, `stopping`, `stopped`.

`get_run({"runId":"RUN_ID"})` → a full run including `id`, `trigger_id`, `state`, rendered `prompt`, full `context`, `activity`, execution metadata and `invocation`. Example selected fields:

```json
{"id":"RUN_ID","trigger_id":"JOB_ID","state":"succeeded","prompt":"Clone REPOSITORY_URL and review the latest commit. Focus on regressions","context":{"event-1":{"prompt":"Focus on regressions","data":{"branch":"main"}}},"invocation":{"event_id":"TRIGGER_ID"}}
```

Retain the submitted key for retries. Current `get_run` returns only internal `invocation.claim_key`, not `invocation.idempotency_key`; never pass that internal field back. `get_run_diagnostics({"runId":"RUN_ID"})` returns a diagnostic object with `runId`, `triggerId`, `state`, `execution`, `trace`, `artifact`, `harnessLog`, `activity` and timestamps. These cover launch/prompt/output/cleanup and trace evidence, not credentials. Missing runs return `not_found`.

`report_run_error({"runId":"RUN_ID","reason":"The deployment check found a regression."})` records a bounded, sanitized reason and the authenticated reporter while the run remains active. It does not stop execution or release concurrency. Report the problem, finish any remaining work, then exit normally so Factorize can collect evidence and clean up. An identical retry is idempotent; a different reason returns `error_already_reported`, and a terminal run returns `terminal_run`. Reporter identity comes from the authenticated API key or OAuth grant; credentials are never accepted in the input or returned. A report followed by observer success makes the final run `failed` with source `agent`; observer failure remains a `system` failure and its diagnostics are retained alongside the report. Stopping takes precedence and keeps the run `stopped`.

`rename_run({"runId":"RUN_ID","name":"Release review","expectedName":"First review"})` → `{"run_name":"Release review"}`. Names are trimmed and must contain 1–120 characters. `expectedName` is optional; when supplied, a changed current name returns `stale_run_name` so the caller can reload and reconcile. Missing or cross-tenant runs return `not_found`.

`stop_run({"runId":"RUN_ID"})` → `{"id":"RUN_ID","state":"stopping"}`. Current `kill_run({"runId":"RUN_ID"})` returns the same result and uses the same operation. Both accept starting/running/blocked runs; queued or terminal runs return `operation_failed`. Neither guarantees immediate termination/slot release. Poll `get_run` and inspect cleanup. See [stop/retry](/work/stop-retry).

## Webhook investigation and conditions

`list_trigger_webhook_activity({"triggerId":"JOB_ID","limit":10})` → `{"items":[{"id":"ACTIVITY_ID","provider":"linear","deliveryId":"PROVIDER_DELIVERY_ID","outcome":"accepted","detail":"...","receivedAt":"2026-10-10T09:00:00.000Z"}]}`. Use it for matching/rejected/duplicate/accepted evidence; it is not a full provider event history.

`list_webhook_deliveries({"provider":"linear","triggerId":"JOB_ID","limit":10})` → `{"items":[{"id":"DELIVERY_RECORD_ID","provider":"linear","deliveryId":"PROVIDER_DELIVERY_ID","event":"Issue","outcome":"accepted"}],"nextCursor":null}` (selected fields). Results are newest-first and cursor paginated. Provider/delivery/event/action/outcome filters are exact matches; `q` searches safe diagnostic text. **Current limitation:** `from` and `to` are accepted by the tool schema but the repository does not apply time-range filters; do not rely on them to bound results.

`get_webhook_delivery({"deliveryId":"DELIVERY_RECORD_ID"})` accepts the internal record ID or provider delivery ID and returns delivery metadata plus `timeline` entries with `triggerId`, `outcome`, `detail`, `createdAt`. Prefer the record ID to disambiguate deliveries. Secrets/raw payloads are never returned. Missing records return `not_found`.

`test_trigger_webhook_conditions` input:

```json
{"conditions":{"all":[{"fact":"webhook","path":"$.issue.title","operator":"startsWith","value":"Review"}]},"webhook":{"provider":"linear","issue":{"title":"Review latest changes"}}}
```

Result contains `decision: "match" | "no-match" | "error"` and plain JSON evaluation details. An invalid request/configuration yields `invalid_request`; evaluation failure yields an error decision. This preview does not authenticate the example, route an event, verify live GitHub state or invoke a trigger. See [condition operators and limits](/integrations/events).

Current `get_run` does not include `output`, trace message contents or a client-facing retry key. To inspect findings, open `https://app.factorize.sh/runs/RUN_ID` or use REST trace pagination. `harness_log` is artifact metadata, not log bytes. Retain your submitted idempotency key.

## Common errors and capability boundaries

Tool errors are `code: message`. `invalid_token` needs reauthorization; `insufficient_scope` needs the listed scope; `invalid_request` needs corrected input; `not_found` means the ID is absent from the authorized workspace; `stale_trigger` needs refetch/reapply; `conflict` needs an unused skill or Trigger name; `queue_full` needs capacity; `operation_failed` needs state/diagnostic inspection. Do not repeatedly retry a write with new identifiers after a lost response.

MCP is a selected tool surface, **not full REST parity**. Signup, verification, integration credential management, authorized-client management, provider resource selection, schedule preview, specialized run status/trace pagination and retained-artifact replay have no corresponding tools in this inventory. Some REST operations require an interactive owner session rather than delegated tokens. Use the browser for setup/resource selection and [REST reference](/api/reference) for exact routes, restrictions and schemas. MCP cannot pass your conversational client's credentials to the execution agent.

Trigger creation and updates accept optional `runScopes`, an array of Factorize API scope names. Omitting it on update preserves the current policy; an explicit empty array grants no application scopes to future runs. Triggers granted `triggers:write` can configure this field too. See [run permissions](/work/manual-invocation-permissions) for defaults and credential snapshot semantics.

## Integration API access

In **Integrations**, each connected API integration has an
**Available by default** checkbox. Checked integrations are available immediately
to connected MCP clients. Unchecked integrations require approval for each client
connection. Existing approvals remain valid when default access is unchecked.
Use the integration's **⋯ → MCP access…** action to disable access entirely;
disabling or disconnecting revokes approvals, and re-enabling requires fresh consent.
Trigger runs retain their independent, explicit credential selections.

`get_api_reflection` lists integration references and access instructions.
The reflected HTTP proxy forwards a relative path using the selected integration's stored
credential. The same policy applies to Bearer APIs, GitHub, Linear, model accounts,
Fly.io, exe.dev, Amp, ClickUp, and X. Credentials stay on the server.

| Integration | Path convention |
| --- | --- |
| Bearer API | Relative to its configured HTTPS origin |
| GitHub | GitHub API path, with existing Git/raw/archive routing |
| Linear | `/graphql` with a JSON GraphQL body |
| Model account | Relative to the account's model API prefix, such as `/responses` |
| Fly.io | Fly Machines API path, such as `/v1/apps` |
| exe.dev | `POST /exec` with a `text/plain` command body |
| Amp | Relative to the configured API base, defaulting to `/api/cloud/v1` |
| ClickUp | Relative to `/api/v2`, such as `/team` |
| X | Supported API v2 paths, such as `/2/users/me`, bounded by the connected account’s granted OAuth scopes |

Cloudflare Tail connections contain inbound webhook signing secrets, not
Cloudflare API credentials, so they do not expose an outbound API.

### Bounded proxy responses

MCP `request_api` defaults to a 4 KiB complete serialized result, including text
and structured content. `maxResultBytes` accepts 2048–32768 bytes. Larger bodies
are streamed into bounded object-storage blocks and returned as an identity-bound
handle/resource link with a preview. Original bytes are preserved. Handles expire
after 30 minutes; every read rechecks current integration access and revocation.

Use `query_api_response` with `mode: json` and a JMESPath field/projection/filter,
`mode: text` for paged lines, or `mode: bytes` for byte ranges. `offset` and `limit`
page the selected results. JSON/text parsing is limited to 1 MiB; larger or binary
responses remain readable as byte ranges. Functions, root references and
constructors are excluded to bound intermediate query allocations. A value that
cannot fit requests narrower selection rather than silently dropping fields.

`read_api_response` retains its REST base64 byte-chunk contract; MCP reads use
smaller bounded chunks. Standard resource reads are optional conveniences; no
client must support resources to retrieve the same data. Upstream pagination and
field projection remain explicit API path/query parameters.

### Slow requests and upstream streams

For external OAuth MCP clients, `request_api` starts a durable operation by
default. Supply a stable `idempotencyKey` to safely recover an interrupted
submission. Use `get_api_operation`, `read_api_operation` and
`cancel_api_operation`; completed operations expose a `responseHandle` for
`query_api_response`. Hosted Pi retains synchronous calls by default while
holding its execution lease; any client may explicitly choose
`execution: async` or `execution: sync`.

Polling works without progress notifications or resource subscriptions. Optional
progress notifications describe the MCP call; upstream progress is the persisted
operation size/state. SSE and chunked HTTP bodies are retained as original bytes,
so event boundaries can span reads. A non-2xx response is a completed HTTP request
with its upstream status, not a claim that the upstream action succeeded.

Limits are fixed at 32 MiB request, 64 MiB response and 15 minutes upstream time.
Failures surface a code, retained-byte count, partial flag and uncertain-effect
flag. Cancellation cannot undo an upstream write. Interrupted dispatch is never
replayed automatically; retrying the same operation ID does not issue it again.

### File and generated request bodies

Call `create_payload` to reserve a temporary connection/run-bound handle. For an
existing file, open its authenticated `browserUploadUrl`, upload directly, and
return to chat with the handle. No run is required. ChatGPT clients supporting
native file parameters can instead call `import_attachment`; other clients use
the same upload-page fallback. Malformed or expired native download URLs produce
an actionable error rather than an attempt to reconstruct file bytes.

For generated text, use `append_payload_chunk` at the returned byte size, then
`finalize_payload`. Identical chunks at the same offset are idempotent. Finalized
payloads are immutable and have a SHA-256 checksum. `fetch_payload` imports file
bytes from an authorized integration without passing them through the model.

Pass `bodySource: {"kind":"payload","handle":"..."}` to `request_api` for a raw body.
Sources can also be authorized retained `response` handles or `artifact`
references containing `runId` and `artifactId`. Use `multipart` parts with names,
optional filenames/media types, and a source or small text value for form uploads.
The 32 MiB request limit includes multipart framing. Payloads expire after 30
minutes; reads and writes recheck the originating identity.
