## Events and occurrences

`list_events` and `get_event` discover Event definitions and their payload
schemas. `create_event` and `update_event` manage those definitions. Each Event
may have multiple Triggers. An enabled Trigger publishes an occurrence only
after validating the payload against the Event's current JSON schema.

Subscribe to `factorize://events/{eventId}/occurrences` using MCP resource
subscription support. After a resource-updated notification, read the resource
to retrieve durable data. `list_event_occurrences` lets a reconnecting client
recover stored records.

MCP Events clients discover the stable `factorize.occurrence` type with
`events/list` and subscribe using `arguments: { "event_id": "<uuid>" }`.
Get the UUID from `create_event` or `list_events`; no plugin refresh is
needed for new Event definitions after the one-time catalog refresh. Reuse the
same name, arguments, and callback to renew or unsubscribe. Existing per-Event
subscriptions keep their original names and continue receiving webhooks.
Each notification includes the occurrence and definition IDs. Call
`read_event_occurrences` with `occurrenceId` for the committed payload. For a
wake without an ID, call it with the saved `definitionId` and a recent `since`
time, and follow `nextCursor` with the same definition and time. Windowed reads
use recorded time so recent arrivals with older source timestamps appear.
Reads leave history intact.

Use `read_event_delivery_diagnostics` with an exact `occurrenceId` to
inspect outbound MCP webhook delivery. `no_delivery_records` means the
occurrence exists but no delivery rows are recorded; a missing occurrence
returns not found. Rows distinguish pending/sending, accepted, failed, and
cancelled delivery. They show opaque subscription IDs, attempt counts, safe outcome codes, HTTP status,
and timestamps, never payloads or callback details. Callback acceptance is
not proof that a downstream task ran. This is separate from inbound webhook
delivery tools and cannot retry an outbound message.


`delete_event` permanently removes the Event, all attached Triggers and input
configurations, and all stored occurrences.

### Optional processing acknowledgments

The standard MCP subscription request and HTTP delivery behavior are unchanged.
HTTP 2xx means the callback accepted the wake, not that a task ran. Opt in for
future occurrences on the exact subscription using
`set_event_processing_acknowledgments` after subscribing. The setting is off
by default. The same active OAuth grant with `triggers:read` can read it with
`get_event_processing_acknowledgments`.

- Acknowledge promptly **after** durable processing or handoff. Call
  `acknowledge_events` with the exact `subscription_id` and successful original
  `event_ids` from `data.occurrenceId`. Arrays accept 1–100 UUIDs. An ACK
  reports newly processed, already processed, and not acknowledged IDs; do not
  treat the last group as completed work.
- A wake may arrive out of order or contain only part of the work. A recovery
  webhook may use a fresh top-level `eventId`; read and deduplicate by the
  unchanged original `data.occurrenceId`. UUIDs do not imply ordering or a
  high-water mark. Do not assume a platform batch window, run cap, or check
  cadence. Page durable history by its documented cursor and retain any work
  you cannot complete; do not silently drop it.
- To rate limit, pace in your client first. An optional `cooldown_seconds`
  (1–3600) on an ACK with newly completed work pauses delivery only on that
  subscription. Retrying the same ACK does not extend cooldown. Delayed
  delivery remains durable and resumes when cooldown expires even without a
  new event.
- If the ACK timeout expires, Factorize sends bounded recovery wakes for that
  original occurrence. Use `read_event_delivery_diagnostics` to distinguish HTTP
  acceptance from awaiting ACK, processed, waived, cancelled, and exhausted.
  `replay_unacknowledged_events` queues exact unresolved IDs on your active
  opted-in subscription, subject to cooldown; it does not create business
  occurrences or replay completed work.
- Turning off waives unresolved acknowledgments, cancels unstarted recovery,
  and clears subscription cooldown. Turning it on again applies only to
  future occurrences. A reactivated subscription is a fresh generation and
  starts with acknowledgments off.


## Triggers

A Trigger belongs to one Event and watches a schedule, signed webhook/provider
input, or manual fire request. Duplicate deliveries are deduplicated. Reuse the
same `idempotencyKey` after an uncertain manual fire. Webhook activity tools
show safe processing outcomes without exposing secrets or raw payloads.

`create_trigger` and `update_trigger` require a parent `eventId` and an
explicit `sources` array of input configurations. For a manual-only Trigger,
send `sources: [{ "kind": "manual" }]`. Read a Trigger before replacing its
configuration.

## Integration APIs

Integration tools use server-held credentials and current authorization; credentials are never
returned. `get_api_reflection` describes available integrations and safe request
examples before `request_api` is used. See [REST reference](/api/reference) for
exact request and response schemas.

## VM permissions

Use `grant_vm_permissions` to enroll an existing Machine through a team VM
provider connection. Supply the team's integration ID as `providerId`, the
Machine ID as `vm`, and the Fly app name as `app`. Create a request key once and
reuse it for retries. Initial enrollment requires a running Machine with
`curl`, `openssl`, and permission to use the Fly OIDC socket in the guest.

```json
{
  "target": {
    "kind": "machine",
    "providerId": "9dd924e0-3a35-48d5-bcd1-56e4b0922265",
    "vm": "1234abcd",
    "app": "my-app",
    "requestKey": "my-app-workload-1"
  },
  "permissions": { "scopes": ["triggers:read"] }
}
```

Use `permissions.presetId` to apply a preset. Factorize saves its current
scopes and rejects the entire request if any requested scope is outside the
caller's effective access. To replace permissions, supply a `target` with
`kind: "existing"`, `grantId`, and `expectedRevision` from `list_vms`. Revoking
a grant removes its Factorize permissions while the workload keeps running.
Enrollment is available only for providers enabled after identity validation.

### Authenticate from an enrolled Machine

On Fly.io, request an OIDC token through the `/.fly/api` Unix socket. POST
`{"aud":"<grant authentication.audience>"}` to `http://localhost/v1/tokens/oidc`.
Keep the private key in the guest at the returned `authentication.guestKeyPath`,
relative to the enrollment user's home directory.

For each REST or MCP HTTP request, set these headers:

- `Authorization: Bearer <provider OIDC token>`
- `X-Factorize-VM-Grant: <grant ID>`
- `X-Factorize-VM-Proof: <signed proof JWT>`

Sign the proof with the enrolled P-256 private key. Use JWT header fields
`alg: "ES256"` and `typ: "factorize-vm-proof+jwt"`, and encode the signature in
the 64-byte JWS format. Include these claims:

| Claim | Value |
| --- | --- |
| `grant` | Grant ID |
| `ath` | Unpadded base64url SHA-256 of the provider token |
| `htm` | HTTP method |
| `htu` | Absolute request URL, including its query string |
| `jti` | A new UUID for each HTTP request |
| `iat` | Current Unix time in seconds |

Send the proof within 60 seconds and sign a fresh proof for every retry. MCP
workloads need a transport that can set dynamic HTTP headers. The VM uses
the scopes in its saved grant and refreshes its provider token before expiry.
