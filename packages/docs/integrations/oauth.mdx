---
title: Integration access
description: Connect external services used by Trigger inputs and MCP clients.
---

Integrations hold server-side credentials used to validate provider webhooks or
make authorized API requests. Select only the integrations needed for your
Triggers or MCP connection. Credentials are encrypted and never returned by
Factorize APIs.

Bearer API, GitHub, Linear, ClickUp, X, Fly.io, exe.dev, Amp, and Cloudflare REST API
integrations have distinct setup flows. Cloudflare Tail is retired. Use the browser's Integrations page to connect or revoke
credentials and to choose which MCP clients may access them.

Choose **Delete** on a supported integration to preview its impact, then confirm.
Deleting removes the connection from Factorize, not the provider. For Linear,
Factorize removes its saved OAuth connection and webhook routing for that
workspace. Affected Trigger sources, Event lookups, and client or workload
access are listed before confirmation. A Trigger with no sources left is
removed, but Event definitions, subscriptions, and recorded occurrences are
kept. Reconnecting does not restore removed configuration or grants.


### Hetzner Cloud

Add the project in **Integrations → Hetzner Cloud** with a Hetzner project
token. Check **Hetzner Cloud** in an OAuth client's permissions to allow it
to use the native API and its enrolled SSH access. Unchecking it removes
both immediately; neither change requires reconnecting the OAuth client.

Hetzner enforces the project token's permissions. Choose **Read** for inventory
only. With a **Read & Write** token, checked clients can make changes, delete
resources, and incur charges. The existing client checkboxes are unchanged
by this update: a client already checked for a project with a Read & Write
token can make writes immediately. Replacing the project still resets client
API grants and probe enrollments; reassign only clients that need API access.
Client SSH key pairs stay attached to the client, independent of the project.

Use `get_api_reflection` to find the authorized Hetzner connection ID. Then
use the standard `request_api` tool with the method, relative `/v1/...` path,
query, and JSON body described in the [Hetzner Cloud API](https://docs.hetzner.cloud/reference/cloud).
For example, list servers using `GET /v1/servers`. To create a server, use
Hetzner's native `POST /v1/servers` body. Factorize does not rewrite it or
return the project token. Hetzner enforces the token's access. As with other
proxy connections, OAuth also needs `proxy:use`; Hetzner's checkbox controls
access to the specific project and is rechecked before dispatch and before
retained results can be read. The proxy defaults to asynchronous execution.
Use a stable `idempotencyKey` for a write and inspect the operation instead of
repeating an uncertain request.

#### Factorize SSH key management

`get_hetzner_ssh_public_key` returns the calling OAuth installation's public
key and a restricted authorized-keys line. Private keys are encrypted and
not exposed. Owners and their authorized clients can use Hetzner's native
SSH-key API through the proxy. A Hetzner project SSH-key record by itself
does not install a key on an existing server. During native server creation,
Hetzner's `ssh_keys` field places keys according to the selected image's
defaults. To use Factorize's authentication check, configure the complete
restricted key line on a dedicated non-root account, then independently
obtain the host's Ed25519 fingerprint from a trusted console. In **View
servers**, the owner enrolls that account, selects the exact OAuth client,
and sets the trusted fingerprint. Existing enrollments created by Factorize's
former server tool retain their original client binding.

`check_hetzner_ssh` revalidates project membership and the pinned public IPv4
for the client's enrolled server, proves fresh authentication with the
pinned host key, and closes immediately. It never starts a shell, runs
commands, or returns output. Remove the installed public key on the server
when retiring access; removing a connection in Factorize does not change
the server.


### Run commands over SSH

The SSH server decides whether a client can log in. Ask the connected client
to call `get_ssh_public_key`; add that public key to the account it should use.
For a new Hetzner server, use the native Hetzner API through `request_api`.
Use a dedicated non-root account and discover its host fingerprint through a
trusted provider console. An owner then saves the public IP, username, and
fingerprint using `POST /api/v1/ssh/targets` from an authenticated owner session,
and supplies the returned target ID to the client. No private key is exposed.

`ssh_exec` takes that target ID and one command. It returns stdout, stderr
and the exit code, with a truncation flag if output exceeded the response
limit. Commands do not share a shell, working directory, or environment.
The broker can reuse the authenticated connection for up to 30 seconds
idle and no more than two minutes in total. A timed-out command may still
have run; do not retry without reconciling its effects.

For an existing Hetzner Cloud server, list the project inventory through
`request_api` or open **View servers** in Factorize. In **SSH commands**,
choose the server and save its independently verified Ed25519 host
fingerprint and the SSH username. The client can then call `ssh_exec`
with `hetznerServerId` instead of `targetId`. Factorize checks the connected
project and resolves its current address through Hetzner; it never trusts the
first SSH response. A changed host fingerprint stops execution and requires
verification again.

The Hetzner checkbox governs provider access, including the server-ID lookup.
It does not install or remove authorized keys on the server and does not
govern generic targets selected by `targetId`. Removing an authorized key on the server denies fresh
SSH connections; terminate the existing connection on the server too if
revocation must be immediate. Previously installed probe-only keys remain
probe-only unless the server operator changes the authorization.
