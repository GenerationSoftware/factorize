Factorize accounts own dashboard identity. Sign up with an email and password, verify your email to sign in automatically, then open [Integrations](https://app.factorize.sh/integrations) to connect Linear when using Linear-backed triggers. Linear OAuth only connects the workspace; it never signs you in. Register `/auth/linear/callback`, configure issue and issue-label webhooks at `/webhooks/linear`, and store the client credentials and signing secret as Worker secrets. ClickUp is optional: register `/auth/clickup/callback`; connecting it automatically registers its task webhook. GitHub uses an installed GitHub App, while exe.dev and Cloudflare Tail connections are configured in Integrations.

| Account | Browser action and required access | Verification |
| --- | --- | --- |
| exe.dev | Add an account-level token, test credentials, and save. VM configurations select workspace images and tags; managed agents use hosted Pi with a separate model integration. Needs VM listing/creation/SSH/deletion, per-run WIF integration management and exclusive VM attachment; see [operations](/self-hosting/operations). | Test connection, then `list_execution_configs`; optionally diagnose the saved connection. |
| Linear | Connect Linear and approve the workspace. Your account must access the selected project and issues; organization policies may require an administrator. | Select project/rules in the browser editor, send one matching event, inspect delivery/run. |
| ClickUp | Connect ClickUp and approve the intended workspace/team with access to the list/tasks. | Select list/rules, change one matching task and inspect delivery/run. |
| GitHub | Connect GitHub to install/authorize the Factorize App on the intended account/repositories; organization approval may be required. | Confirm active installation and repository selection, then send a matching event. |

The provider consent/installation screen is the authority for granted permissions. Grant access to the selected resources; changing those resources can require provider reauthorization. Trigger-event access and execution-agent access are separate: select an existing GitHub installation or Linear connection in each trigger to authorize its backend proxy access. Factorize reuses those credentials and their existing upstream permissions; it does not deliver tokens to the VM.

MCP exposes safe connection/installation/target metadata, not tokens. Account connections, resource pickers and credential management require browser setup. Reconnect Linear/ClickUp from Integrations; use GitHub's Configure installation link for repository access and verify the installation is active. Do not disconnect integrations while triggers still reference them; update those triggers first.

After changing access, create one controlled event and use `list_webhook_deliveries`, `get_webhook_delivery`, `list_trigger_webhook_activity`, and `list_runs` to verify delivery and execution. See [triggers not firing](/troubleshooting/events). Hosted Factorize manages OAuth application registration, callbacks and webhook infrastructure. Operators of their own deployment use [configuration](/self-hosting/configuration).


## Credentials selected by a trigger

In Integrations, add custom bearer credentials with a fixed HTTPS
origin. Add model integrations with an OpenAI-compatible provider URL and an optional API key. Factorize encrypts credentials on the server. Stored secrets cannot be viewed. A keyless provider requires only its URL. Model IDs and optional effort are selected in Team defaults, Triggers, or direct run overrides, independently of VM configuration.

Select only the bearer integrations, GitHub installations, Linear connection and model integration that each Trigger needs. Pi runs in Factorize and uses MCP tools. VM scripts retain their own workload lifecycle.
Each run uses its saved selection and Factorize API scope snapshot; later trigger
edits affect future runs. Disconnect revokes existing run access permanently,
even after reconnecting the same account. Select a replacement explicitly for
future runs. Missing selections remain visible for repair and are never
silently replaced with all available credentials.

exe.dev and Fly guests use a localhost helper that authenticates to Factorize
with fresh vendor signatures bound to that exact VM/run. Selected upstream
credentials stay in the backend. Canceling or terminating a run removes its API
and outbound access, independently of external VM deletion retries.

## MCP API proxy access

External MCP clients continue to authenticate with OAuth; execution VMs continue
to use vendor OIDC. These identities have separate grants. Run selections never
inherit an external client's approvals.

In Integrations → MCP API access, choose a policy for each custom
bearer integration, GitHub installation, Linear connection, and model account:

* **Baseline:** immediately available to all active MCP authorizations. Removing
  baseline access immediately removes access derived from that policy.
* **Requestable:** visible in reflection, but each separately authorized
  connection must obtain consent before use.
* **Disabled:** unavailable for requests and consent. Disabling or disconnecting
  permanently invalidates existing integration approvals. Re-enabling as
  requestable requires fresh consent. Replacing a credential without deleting
  its integration preserves approvals.

Start OAuth with only the Factorize resource scopes your client needs; do not
request the complete integration catalog. `get_api_reflection` returns the
current agent identity, effective Factorize scopes, integration references,
readable names and descriptions, instructions, access state, connection
availability, and the required integration scope. Availability describes stored
connection state, not a guarantee that an upstream credential is healthy.

POST JSON to the reflected `proxy.requestUrl` with `integration`, an HTTP `method`, a relative `path` including
an optional query, optional safe `headers`, and optional `body`. `encoding` is
`utf8` by default or `base64` for binary input. The origin and upstream
credentials are selected by Factorize. A grant covers the whole integration,
bounded by the credential's upstream permissions. Redirects are rejected.

Missing requestable access produces an HTTP 403 response with a
`WWW-Authenticate: Bearer` challenge containing `error="insufficient_scope"`,
`scope`, and `resource_metadata`. Reauthorize with the union of your currently
needed scopes and the challenged scope, approve the named integration in the
browser, exchange the new code, then retry. The new authorization is independent
of other connections, including copies of the same client. Refresh retains the
authorization identity; a narrowed token uses only its presented scopes.
Integration scopes have the form `integration:{reference UUID}:{revocation epoch}`;
use the value returned by reflection rather than constructing or caching it.

Responses preserve the upstream `status`, safe `headers`, byte `size`, and body.
An upstream non-2xx status is distinct from a local authorization or proxy error.
UTF-8 responses of up to 32 KiB return inline with `encoding: "utf8"`; binary
responses use `base64`. Larger responses are consumed into R2 and return a
`handle` and `expiresAt`.

POST JSON to `proxy.readResponseUrl` with the handle and a byte `offset` (initially zero).
Chunks are always base64, up to 64 KiB; use `nextOffset` until `done` is true.
Handles are tenant/identity bound, expire after 24 hours, and recheck access on
every read. Revocation blocks subsequent calls and reads but cannot undo an
upstream action already accepted. Existing VM proxy URLs retain true streaming.

The same operations are documented under `/api/v1/agent/reflection`,
`/api/v1/agent/requests`, and `/api/v1/agent/responses/read`. Authorize `proxy:use` to use the HTTP proxy with the agent credential. Existing MCP authorizations without this scope require renewed consent. Other REST operations retain their own authentication requirements. MCP clients use `request_api` and `read_api_response` with the same validated arguments and authorization as these HTTP endpoints. Owner policy endpoints require an interactive browser session. In **Settings → Authorized clients**, choose **Edit permissions** to disable or restore originally authorized Factorize scopes. For each integration, choose **Default** to follow workspace policy and OAuth consent, **Allow** to approve the current integration, or **Block** to deny this connection access. Disabling or disconnecting a workspace integration invalidates per-connection approvals. Edits apply to subsequent requests from this connection and its delegated VMs. Owners can also revoke a connection. MCP clients can set their own connection label with `rename_mcp_client`.

The scheduler maintenance heartbeat removes expired response objects and their
PostgreSQL receipts. A receipt exists before any R2 block is written, including
interrupted/unreturned responses. Object deletion failures retain receipts for
retry. Operators must retain the scheduler and RUN_ARTIFACTS binding when
rolling out migration `0054_agent_api_grants`.

## External VM access

Start Codex with the device login helper from the Factorize checkout:

```sh
node scripts/agent-login.mjs codex
```

Approve the displayed code. The helper sets the short-lived Factorize credential for the child process and configures the Factorize MCP connection to use it. Supply additional integration scopes from reflection in the space-separated `FACTORIZE_SCOPES` environment variable on a subsequent login. In a shell with this environment, send JSON to the reflected request URL using `curl -H "@$FACTORIZE_AGENT_AUTH_FILE" --json ...`. The file is private to your OS user and the helper removes it when the child exits. For exe.dev, send method `POST`, path `/exec`, headers `{"Content-Type":"text/plain"}` and a command in `body`.

After creating a VM, call `grant_vm` with the provider integration ID, VM name, selected integration IDs and an idempotency key. The guest reads its WIF token and local proof using the receipt instructions. Both authenticate only the reflected HTTP proxy operations. Grants expire with the issuing access token. Access through independent provider-native integrations is outside this grant. Revocation removes the Factorize identity integration and leaves the VM running.
