A **run** is one accepted execution in a project. It records the prompt, inputs, execution configuration, permissions and outcome. An agent can start one directly with a prompt and an optional launch skill such as `dev`. A **job** is a saved template for creating runs. Its **triggers** can invoke it manually, on a schedule, on a provider event, or in response to another job's lifecycle. Both paths use the same queue and execution backends. An **execution integration** supplies the account and agent configuration.

The **conversational agent** you talk to uses MCP to control Factorize. The **execution agent** receives the run's resolved prompt and does the work on the execution account. Giving the conversational agent MCP permission does not give the execution agent repository, provider or model access. Your saved connection, VM tags and prompt must supply those.

Every job gets a manual trigger. Additional triggers have immutable server-generated slugs such as `trigger-2`. Each run receives only the firing trigger's context; [prompt templates](/work/prompts) use that slug.

## Concurrency and the queue

A project owner enables direct launches by saving a VM configuration in **Project settings → Direct run defaults**. The project concurrency limit applies to both direct and job-created runs. The project can also hold that many waiting runs. Each saved job has its own concurrency limit within that capacity.

With job concurrency 1, a review already running occupies the only active slot. One more run may wait in the queue. A further manual request returns `queue_full`; wait for capacity instead of repeatedly changing retry keys. Automatic schedule/webhook/lifecycle signals arriving while a run is queued are skipped/coalesced, so they are not a complete event log. An accepted idempotency key still returns its original run even when the queue is full.

Job concurrency can be 1–50. With job concurrency 2, two reviews may execute and one may wait. Queued runs keep the prompt/context they were submitted with; editing a job does not rewrite those runs. Query runs and the provider for authoritative work when automatic events coalesce.

Inspect output before treating a terminal state as a useful result. Trace collection can be incomplete even when execution completed; advanced trace recovery belongs in [operations](/self-hosting/operations).

## Code jobs

Choose **Code script** in the job editor to run a shell script on the configured exe.dev VM image. Code jobs do not need a prompt, model, effort, skill, or agent executable. The process runs as `exedev` in `/home/exedev/workspace`.

The script receives `FACTORIZE_RESULT_PATH`, set to `~/.factorize-job/results.json`, and `FACTORIZE_INPUT_PATH`, set to a JSON file containing the trigger context. For example:

```sh
#!/bin/sh
set -eu
count=$(jq -r '.source.outputs.count // 0' "$FACTORIZE_INPUT_PATH")
printf '{"status":"succeeded","summary":"Exported %s records"}\n' "$count" > "$FACTORIZE_RESULT_PATH"
printf 'count=%s\n' "$count" > "$HOME/.factorize-job/export.txt"
```

The structured result determines run success or failure. Other files written under `~/.factorize-job/` are retained as downloadable artifacts. Each queued run snapshots its script and input context, so later job edits do not change it.

Skills are reusable, tenant-scoped instruction bodies that can be attached to jobs in an explicit order. A body is literal text: Mustache expressions, braces, Unicode, whitespace, and HTML-like text are passed through unchanged. Only the job context is rendered with trigger data.

Renaming a skill changes its shared key without changing stable job references. Deletion is rejected while any enabled or disabled saved job uses it. A run resolves its selected skills when queued and stores the exact bodies, keys, revisions, and order; later edits, renames, or deletion do not change historical runs. Skill library operations require `skills:read` or `skills:write`; inspecting affected jobs also requires `jobs:read`.
