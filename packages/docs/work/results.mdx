---
title: Inspect results
description: Read run state, output, prompt, and trigger context.
---

Ask: “Show the latest runs for this job and summarize the completed review.” Use `list_runs({"jobId":"JOB_ID","limit":10})`, then `get_run({"runId":"RUN_ID"})`. Current MCP does not return an `output` field or trace messages. Open the browser run page to read the trace, or retrieve REST trace pages with an authorized client. Report the state/link through MCP and only summarize findings after actually reading them.

Run pages return `items` and `nextCursor`; send that cursor for the next page. Optional `state` and `contextQuery` filter runs. Context search is a case-insensitive substring, not a query language. Current list rows contain no context excerpt; `get_run` returns full `context`, rendered `prompt`, `invocation.trigger_id`, execution metadata and activity.

Check that the intended trigger fired, the repository/task appears in the rendered prompt, and the browser/REST trace supports the reported result. A queued submission is not a successful execution. Browser run pages are at `https://app.factorize.sh/job-runs/RUN_ID`. Agent output stays in Factorize and is not automatically copied into Linear.

New agent runs must write a JSON result envelope to the absolute path in `FACTORIZE_RESULT_PATH` before exiting. The object requires `status` (`succeeded` or `failed`); it may include a `summary` and an `outputs` JSON object. Failed results require a non-empty `reason`. The file is limited to 64 KiB. A zero process exit without a valid `succeeded` result is a failed run. Put additional run files in `~/.factorize-job/`; regular files up to 10 MiB each (100 files, 50 MiB total) are retained. Symlinks and paths outside that directory are not collected. Run details show the result and authorized downloads.

For missing output or execution failures, call `get_run_diagnostics` and follow [failed-run troubleshooting](/troubleshooting/runs).

Failed runs keep the existing `failed` state filter and legacy `failure_source` enum (`system` or `agent`); `agent` maps to the canonical `failure.source: "run"`. New read responses include nullable `failure: { source: "run" | "system", code, reason }`. A null value means the historical evidence is unknown, not that the row was successful. Old rows that only have `failure_source="system"` are not treated as confirmed infrastructure failures.

Classification is based on execution evidence, never text in agent-controlled JSON. A failed structured result, missing/invalid required result, or unsuccessful agent process exit is a run failure. Launch/provisioning failure, unavailable run-owned VM, or disappeared supervisor is a system failure. A successful process and successful result has no failure. A successful result cannot override an unsuccessful process or an accepted `report_run_error`; when multiple task reasons disagree the first persisted execution/result failure is primary and explicit report provenance remains in `agent_error`. Independent infrastructure evidence takes system precedence. Result protocol failures are recorded as the failure reason, not as `artifact_error`. `artifact_error` remains reserved for artifact, trace projection and cleanup diagnostics.

Protocol version 0 runs keep optional-result compatibility. Protocol version 1 requires a valid result envelope (strict fields, maximum 64 KiB); malformed, oversized, missing or schema-invalid files fail the run. The result and report-error schemas do not accept a failure source or infrastructure provenance.

Historical repair is evidence based. Migration `0032_run_failure_outcomes.sql` only repairs failed rows with `job_result.status="failed"`, a successful execution diagnostic, systemd `Result=success`, and exit status 0. It clears `artifact_error` only when it exactly equals the structured task reason. Before rollout, run this read-only audit and retain its counts with a database snapshot:

```sql
SELECT count(*) AS proven_run_failures,
       count(*) FILTER (WHERE artifact_error=job_result->>'reason') AS exact_misplaced_artifact_reasons,
       count(*) FILTER (WHERE artifact_error IS NOT NULL AND artifact_error IS DISTINCT FROM job_result->>'reason') AS retained_artifact_diagnostics
FROM app.runs
WHERE state='failed' AND failure_source='system'
  AND job_result->>'status'='failed'
  AND execution_diagnostics->>'state'='succeeded'
  AND execution_diagnostics->'systemd'->>'result'='success'
  AND execution_diagnostics->'systemd'->>'execMainStatus'='0'
  AND coalesce(job_result->>'reason','') <> '';
```

Roll forward with the additive migration before serving the new UI/API. Roll back application code separately and leave repaired outcome data intact; the old API ignores the new columns. Do not reverse the repair by changing every `agent` source back to `system`; unknown historical rows remain unknown.
