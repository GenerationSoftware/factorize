# Credential proxy cutover and recovery

This procedure describes the required breaking cutover; it is not evidence
that the cutover has shipped. In the current repository checkpoint, the old
proxy provisioning, pairing, and unlock paths are still wired into the API,
settings UI, and scheduler. Do not execute this procedure until those paths
have been removed and the new backend release is verified.

This is a breaking migration. The previous per-owner Fly credential proxy,
browser pairing, and user-held unlock key are not compatible with the Factorize
backend run proxy. Do not run the cutover until the backend release containing
vendor-verified VM identity and tenant-selected run credentials is deployed and
the acceptance checks for both execution providers pass.

## Before the cutover

1. Announce a maintenance window and pause schedules, webhook triggers, and
   other dispatch sources for affected jobs. Prevent new runs from starting
   while the inventory is being prepared.
2. Inventory each tenant's jobs, selected portable integration IDs, model
   account IDs, and the owner of each credential. Keep this inventory private;
   it must contain identifiers and owners, never secret values.
3. Let active runs finish. For runs that cannot finish, stop them through the
   Factorize run controls and verify that each is terminal before proceeding.
   Do not stop a shared execution app or VM to drain one tenant's runs.
4. Confirm the new backend is healthy and that a canary run can use only its
   selected credentials. Check both exe.dev and Fly runs, including a run with
   no portable credentials and one with explicit selections.

If any run is still active or cannot be confirmed terminal, pause the cutover.
Do not revoke its old proxy access while it is running.

## Retire the old proxy

1. In the owner settings, disable the old credential proxy and revoke its run
   enrollment before removing any resource. Verify that it no longer accepts
   new runs. Disabling the proxy does not stop agent VMs; the drain step above
   is required.
2. Identify the proxy Machine from the owner's saved Factorize proxy record.
   Confirm the recorded Fly app and Machine ID in the Fly dashboard before
   stopping it. Stop the proxy Machine and verify its stopped state. Do not
   stop execution Machines as a substitute.
3. After the stop is verified and no old run depends on it, destroy the proxy
   Machine and retire the proxy-only Fly app, deployment secret, browser
   pairing, and control credential. Keep the owner's Fly connection and all
   execution configurations. Remove obsolete proxy-specific deployment
   settings from the backend only after the new backend release is serving
   traffic.
4. Do not copy the old proxy's unlock key or decrypt old ciphertext into the
   new service. The old user-encrypted secrets cannot be migrated by Factorize.

Use the Fly dashboard or documented Fly CLI commands for resource retirement.
Record the app and Machine identifiers that were removed, but never record
credentials, unlock keys, or decrypted secret values.

## Reconnect credentials and repair jobs

1. Each owner reconnects GitHub and Linear using the existing Factorize
   connection flow, reconnects model accounts, and re-enters custom bearer
   credentials. Re-enter the same intended account where possible; a new
   connection ID is expected.
2. Compare the new connection metadata with the private inventory. Update each
   affected job to select the corresponding new credential ID. The cutover
   must not select every tenant credential automatically. A job that cannot
   be mapped confidently stays disabled until its owner repairs it.
3. Verify each saved selection belongs to that job's tenant and that the
   selected account is connected. Run one canary per repaired job and confirm
   its outbound requests use only those selections. Confirm Factorize API
   scopes match the job's configured scopes.
4. Keep jobs with no portable selections unchanged. Do not add a credential to
   a job merely because it was available to the retired proxy.
5. Resume dispatch only after the affected job inventory is reconciled. If a
   credential cannot be reconnected, leave that selection unavailable and the
   job disabled; do not substitute another credential silently.

## Recovery

If the new backend canary fails, keep affected jobs paused and repair the new
backend or the specific credential selection. The old unlock architecture is
not a rollback path. Re-enable an old proxy only if the deployment has not
retired it, its identity is still verified, and an operator has confirmed that
doing so will not reintroduce access for unrelated tenants or runs. Never
restore old credentials or ciphertext from a database backup as part of
rollback. Re-enter or reconnect credentials after service is restored.

## Completion record

Record the maintenance window, terminal-run count, retired proxy app/Machine
identifiers, repaired job count, jobs left disabled for owner repair, and
canary results. Keep secret values, bearer tokens, unlock keys, and decrypted
credential material out of the record.
