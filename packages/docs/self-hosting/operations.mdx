Use the [deployment runbook](https://github.com/GenerationSoftware/factorize/blob/main/docs/package-migration.md) and [trace rollout runbook](https://github.com/GenerationSoftware/factorize/blob/main/docs/trace-rollout-runbook.md) for retention, canary gates and rollback. `npm run check` checks package boundaries, generated contracts, runtime tests and builds. The PostgreSQL auth suite uses an isolated database; see configuration for migration verification.

`get_run_diagnostics` exposes declared trace sources, projection evidence, artifacts and fallback use. A trace may be partial when collection fails. A `matched` reconciliation result verifies the live prefix against the terminal artifact; missing evidence does not prove completeness.

Trace replay is REST-only and requires an interactive owner session with `runs:write`: `POST /api/v1/runs/{runId}/trace/replay` with a UUID `requestId` and `source` (`primary` or `native_session`). Reuse the request ID after interruption. Limit: ten requests per tenant per minute. Results distinguish projected, already projected, skipped and unrecoverable. Replay preserves artifacts; expired/deleted bytes cannot be recovered. Historical Codex tool calls require retained native session bytes.

Cloudflare Tail infrastructure is optional: use the [Tail relay deployment guide](https://github.com/GenerationSoftware/factorize/blob/main/docs/cloudflare-tail.md). Hosted users still supply their own source Worker/relay integration.

## Per-run exe.dev proxies

The account-level exe.dev token used by the Worker must allow `ls`, `new`, `ssh`, `rm`, `integrations list`, `integrations add`, `integrations attach`, and `integrations remove`. Test the saved connection in Settings; a missing permission must be fixed before launching jobs. The agent VM never receives this account token or its run-proxy bearer credential.

Keep shared Factorize integrations on operator-only attachments, such as a dedicated `human` tag that is never selected for jobs. Do not attach shared Factorize proxies to execution VMs, even when currently read-only, and do not use `auto:all`. Legacy `runs:write` expands to `runs:invoke` and is therefore not read-only. Provisioning checks the control-plane attachments for the configured Factorize origin and fails closed on shared access. Apply the same isolation to any alternate Factorize hostname or proxy alias.

Each run creates a marked `fz-run-<UUID>` HTTP proxy targeting the Worker HTTPS origin, attaches it to that exact VM with `--for=24h`, and discovers it through Reflection. The first proxy preflight requires the deployed `/api/v1/runtime-context` operation. Deploy the API and scheduler together, then check the saved exe.dev token permissions and run a canary before resuming normal dispatch.

Migration `0027_run_proxy_delivery.sql` distinguishes proxy-issued credentials from legacy credentials placed in VM environments. At the code cutover, legacy credentials stop authenticating; they never gain the proxy's read scopes. In-flight legacy agents can still write their result files, but must be restarted if they need Factorize API access. Rollback to the pre-proxy code restores the legacy credential behavior, so review that security implication before rolling back.

Cleanup checks the integration's run ownership marker before removal and retries failures. The scheduler persists its execution handle before external provisioning, so interrupted and partial launches retain cleanup ownership when their launch lease is recovered. Inspect failed cleanup before removing a marked integration manually; never delete an unrelated name collision. VM attachments and credentials expire after at most 24 hours even when external cleanup is unavailable.
