For the breaking migration and job repair procedure, see [Credential proxy cutover and recovery](credential-cutover). The older [credential proxy security runbook](credential-proxy-security) describes the retired standalone proxy and unlock architecture.

`get_run_diagnostics` exposes declared trace sources, projection evidence, artifacts and fallback use. A trace may be partial when collection fails. A `matched` reconciliation result verifies the live prefix against the terminal artifact; missing evidence does not prove completeness.

Trace replay is REST-only and requires an interactive owner session with `runs:write`: `POST /api/v1/runs/{runId}/trace/replay` with a UUID `requestId` and `source` (`primary` or `native_session`). Reuse the request ID after interruption. Limit: ten requests per tenant per minute. Results distinguish projected, already projected, skipped and unrecoverable. Replay preserves artifacts; expired/deleted bytes cannot be recovered. Historical Codex tool calls require retained native session bytes.

Cloudflare Tail infrastructure is optional: use the [Tail relay deployment guide](https://github.com/GenerationSoftware/factorize/blob/main/docs/cloudflare-tail.md). Hosted users still supply their own source Worker/relay integration.

## Per-run vendor identity

The exe.dev account token must allow VM list/create/SSH/delete and integration
list/add/attach/remove. Each run creates one WIF integration, with the run's
unique audience and an exclusive VM attachment. Factorize verifies the vendor
signature and current attachment inventory on admission. A WIF subject identifies
an integration; it is not treated as a VM ID. The account token stays in Factorize.

Keep shared Factorize integrations on operator-only attachments. Do not use
`auto:all` or shared tags to grant broader Factorize API access to execution VMs.
Provisioning and renewal reject shared proxies targeting the Factorize origin.
Apply the same isolation to alternate hostnames and aliases.

Fly uses organization-slug OIDC discovery/JWKS and a fresh token from the guest
`/.fly/api` Unix socket. The backend pins issuer, audience, exact subject and
Machine ID to the active run. Machines live in a tenant execution app with no
standalone proxy Machine. Guest HTTP exec uses the documented Machines API.

Both providers run a root-owned localhost identity helper. It forwards only
the configured backend routes and renews vendor proof for every request. No
Factorize guest bearer, upstream token, browser capability or unlock key is
installed. Cancel/terminal/disconnect checks occur in the backend, so failed
provider cleanup cannot restore access. Artifact finalization during stopping
additionally requires a separately signed upload grant.

The scheduler persists cleanup ownership before provisioning, verifies vendor
identity before launch, and resumes cleanup after interrupted leases. Verify
resource ownership before manual removal; never delete an unrelated collision.
Before deploying migration 0052, follow the credential cutover runbook above.
